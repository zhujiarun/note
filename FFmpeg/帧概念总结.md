# FFmpeg 编解码中的"帧"

## 一、帧的基本概念

帧是视频最小的组成单位。一帧就是一幅静态画面,视频的本质是一组快速连续播放的图像,帧率(fps)表示每秒播放多少帧。这是直觉层面的理解,而在 FFmpeg 的编解码流程中,"帧"至少要从两个层面理解:编码层面的"压缩帧"和 API 层面的 `AVFrame`/`AVPacket`。

## 二、编码层面的帧:I / P / B 帧

H.264/H.265 压缩时不会逐帧保存完整画面,而是将帧分为三种类型:

- **I 帧(关键帧,Intra frame)** — 保存完整图像,可独立解码。它是解码的起点,通常作为随机访问(seek)的锚点。
- **P 帧(Predictive frame)** — 只保存与前面帧的差异(运动矢量、残差),解码时需参考前面的帧。
- **B 帧(Bi-directional frame)** — 同时参考前面和后面的帧,压缩率最高,但引入了解码顺序问题(见下)。

## 三、存储顺序与显示顺序:DTS 与 PTS

由于 B 帧需要参考"未来"的帧,解码器必须先把后面的帧解出来,B 帧才能解码。因此:

- **DTS(Decoding Time Stamp)** — 解码时间戳,决定解码器的输入/输出顺序(即存储顺序)。
- **PTS(Presentation Time Stamp)** — 显示时间戳,决定播放器实际显示画面的顺序。

有 B 帧的流里两者不相同。FFmpeg 中 `AVPacket.dts` 是解码时间戳,`AVFrame.pts` 是显示时间戳。解码器按 DTS 顺序输出,播放器必须按 PTS 重排序后再显示,否则画面时序会乱。

## 四、FFmpeg API 层面的帧:AVPacket 与 AVFrame

这是理解"帧"最关键的区分:

- **AVPacket** — 编码后的压缩数据包,里面是 I/P/B 帧的压缩字节流。存于容器(如 FLV/MP4)中的就是它。
- **AVFrame** — 解码后的原始帧,包含 YUV/RGB 像素数据、宽高、像素格式等。

完整流程:

```
编码: AVFrame(原始帧) --编码器--> AVPacket(压缩包) --muxer--> 容器
解码: 容器 --demuxer--> AVPacket(压缩包) --解码器--> AVFrame(原始帧) --> 渲染
```

排查"丢帧"问题时,要分清是丢了解码前的 `AVPacket`,还是丢了解码后的 `AVFrame`,排查方向完全不同。

## 五、与帧相关的其他高频概念

- **GOP(Group of Pictures)** — 两个 I 帧之间的整组帧。决定 seek 粒度:seek 到非 I 帧位置时,解码器需从最近的上一个 I 帧开始解码。
- **关键帧标记** — `AVPacket.flags & AV_PKT_FLAG_KEY`,用于判断当前包是否 I 帧,播放器倍速/拖动时常以此为依据。
- **场(field)** — 隔行扫描视频中一帧由奇偶两个场组成,处理不当会出现"拉丝"。
- **解码延迟 / 帧缓冲** — 编码器与解码器内部有缓冲,输入输出帧数不一定一一对应,必须用 pts 对齐而不是数帧数。
- **time_base 与帧时长** — `AVStream.time_base`、`av_rescale_q()` 用于在容器时间戳与帧时间戳之间换算。

## 六、在 FLV + WebCodecs 播放器项目中的应用

自研 FLV 解封装器 + WebCodecs 时,这套帧模型几乎一一对应:

- FLV tag 的 `timestamp` 即 PTS;若流含 B 帧(HEVC 常见),WebCodecs 的 `EncodedVideoChunk` 需按解码顺序喂入,并显式传入 `VideoDecoderConfig`。
- 解码器输出的 `VideoFrame.timestamp` 需重新排序后再渲染,才能保证显示顺序正确。
- 关键帧判断同样重要:FLV 中通过 tag type(视频/音频)与帧类型字段判断是否为关键帧,用于 seek、丢帧恢复等场景。

WebCodecs 封装了大量 FFmpeg 层面的细节,但帧类型、DTS/PTS 区分、关键帧处理这些底层逻辑绕不过去。理解 FFmpeg 的帧模型,对播放器的 debug 与优化有直接帮助。
